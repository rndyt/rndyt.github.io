我们可以大致将整个电商交易流程分解为下单、支付、回调三个部分。

# 订单创建

在订单创建阶段，需要首先保证的是一次逻辑下单操作只会创建一笔订单，也就是订单创建需要具有幂等性，防止因为用户多次点击、网络波动等导致的重复请求产生重复订单。

实现这一能力，首先就需要能够唯一地标识业务请求，也就是为每次业务操作分配一个唯一的幂等键，同时引入数据库唯一约束，确保数据库层面上不可能出现重复订单。

但是对于电商这类高并发系统，数据库的性能显然是不足以支持的，这就需要引入 Redis 缓存作为中间层提供并发优化。通过 Redis 的 SETNX 命令，只有成功获得了 Redis 锁的请求才可以进行订单创建的操作，降低数据库压力。在引入 Redis 后，就会出现一个新的问题，如果线程获取 Redis 锁后，还没有完成业务操作就因为异常导致退出该怎么办？

解决方案是锁超时释放+持久化订单状态，Redis 锁都是具有 TTL 的，当锁被释放后，其他请求就可以获取到处理资格。为了让新的线程可以接着jiu

在 MySQL 操作明确返回失败回滚的情况下，可以释放 Redis 分布式锁，让后续请求重新获得执行资格。需要注意这里的释放会通过 Lua 脚本和唯一 Token 来确保只有锁的所有者才能删除，防止出现并发错误。如果 MySQL 执行结果未知，例如数据库连接在过程中断开，这时就需要主动查询订单是否存在，如果存在则返回结果，不存在则进入失败流程。

失败释放的前提是 Java 进程正常工作，可以进行异常处理，那么如果进程在处理过程中挂掉了该怎么办呢？解决思路就是将交易状态持久化到 Java 进程之外，使其他服务实例可以发现未完成的交易并接管后续处理。
